# 출시 관문

`pack.ps1`(스토어에 올릴 zip을 만드는 유일한 길)은 아래 두 기록이 맞을 때만 zip을 만든다. 사용자 승인으로 넘기는 옵션은 없다.

왜: 1.2.0은 사용자가 가볍게 써 보고 내자고 한 승인과 그때까지의 시험 통과만 믿고 냈는데, 출시 뒤 숨은 버그가 10개 넘게 나왔다.
사용자가 많아져 버그 하나가 이탈로 이어진다.

## 1. `last-full-run.json` — 전체 시험 기록(자동)

`node tests/run.js`(이름 거르기 없이, 이 저장소 확장으로)를 돌리면 자동으로 남는다.

- `contentHash`: zip에 들어갈 파일 전체의 지문. 시험 뒤 파일이 한 글자라도 바뀌면 관문이 막는다 → 다시 돌린다.
- `testsHash`: 시험 파일(`tests/run.js`·`tests/lib`·`tests/cases`·`tests/fixtures`) 지문(지문이 확장 파일만 덮어 전체 시험 뒤 시험을 약하게 고쳐도 몰랐음 — 과적합 검토 지적). 계산은 `tools/gate-hashes.js`와 `pack.ps1`이 같은 방법으로.
- `version`이 manifest와 같아야 하고, `allPassed`가 참이어야 한다(흔들린 시험이 있으면 다시 돌려 전부 통과한 기록이어야 함).
- `caseFiles`: 그때 돌린 시험 파일 목록. `tests\cases`에 이 목록에 없는 시험 파일이 있으면 관문이 막는다 — 시험을 새로 넣고 전체 시험을 다시 안 돌리면 그 시험이 관문을 거치지 않고 빠졌다(모양 섞임 시험을 넣으며 찾음). 시험 폴더가 없는 사본(GitHub 사본)에서는 이 확인을 건너뛴다.
- 시험 도중 확장 파일이 바뀌면(`changedDuringRun`) 통과로 남기지 않고, 실행기 끝 줄·종료 코드도 실패로 낸다.

## 2. `review-<버전>.json` — 독립 검토 기록(손으로)

그 판에서 바뀐 코드를 **만든 쪽과 다른 눈**(새로 띄운 검토 에이전트 여러 갈래, 또는 사람)이 버그를 찾은 기록.

```json
{ "version": "1.2.1", "reviewedAt": "…", "reviewers": ["…"], "scope": "무엇을 어떻게 봤는지",
  "reports": [ { "report": "release/overfit-report-<버전>-r3.md", "reportHash": "SHA-256" } ],
  "findings": [ { "id": "…", "summary": "…", "status": "fixed", "test": "시험 이름" },
                { "id": "…", "summary": "…", "status": "wontfix", "reason": "왜" } ] }
```

- `reports`: 지적을 이 기록에서 처리한 중간 회차 과적합 검토 보고서 원문과 그 지문(6절 — 마지막 회차는 `overfit-review-<버전>.json`이 묶음).
- `fixed`: `test`에 적은 시험이 1의 기록에서 PASS여야 한다. 그 시험은 7절의 고치기 전 판 실행 기록에서 PASS가 아니어야 한다.
- `hardening`(예방 조치, 직접 재현 못 함) · `wontfix`(안 고침) · `not-a-bug`(실행으로 아님을 확인): `reason` 필수.
- `superseded`(구현 교체 — 사용자 결정으로 그 지적이 가리키던 구현을 통째로 바꿔 없앰): 그 결정의 사용자 원문 `quote`·그때 물은 글 `question`·`reason`과,
  바꾼 요청인 3절 바뀐 점 기록의 `request` 항목 id `replacedBy`가 필요하다. 지적이 걱정한 것을 새 구현에서 다시 보는 시험 `test`를 적으면 1의 기록에서
  PASS여야 한다. `fixed`가 아니므로 7절의 고치기 전 판 기록은 보지 않는다 — 새 시험을 옛 구현 판에 돌리면 버그가 아니라 조작 방식이 달라 실패하므로
  그 기록은 고침의 근거가 못 된다.
- 그 밖의 상태(`open` 등)가 하나라도 있으면 막는다.

## 3. `changes-<버전>.json` — 바뀐 점 출처 기록(손으로)

왜: 1.2.1의 '작품 저장 확인'은 시험·독립 검토를 다 거쳐 관문을 통과했지만, 원인을 확인하지 못한 제보(작품이 사라짐)에 내 짐작 원인을
놓고 만든 기능이었다(사용자 지적으로 1.3에서 뺌).
시험·검토는 "만든 것이 도는가"만 보고 "왜 있나"는 안 봤다. 그래서 그 판에서 바뀐 점(사용자에게 보이는 기능·고침·뺀 것)마다
출처를 적고 관문이 형식을 본다.

```json
{ "version": "1.3.0", "changes": [
  { "id": "…", "summary": "…", "origin": "request", "quote": "사용자 원문", "test": "확인 시험",
    "fromOption": true, "premise": "preference | 전제를 확인한 시험 이름" },
  { "id": "…", "summary": "…", "origin": "fix", "report": "제보·발견 원문", "reproduced": true, "test": "확인 시험",
    "failsBefore": "고치기 전 판에서 실패한 것" },
  { "id": "…", "summary": "…", "origin": "hardening", "noNewBehavior": true, "reason": "…" },
  { "id": "…", "summary": "…", "origin": "removal", "quote": "사용자 원문", "reason": "…" } ] }
```

- `request`: 사용자 원문이 그 기능을 요청해야 한다. 내가 드린 선택지에 대한 답이면(`fromOption`) 그 선택지들이 깔고 있던 사실 전제를
  시험으로 확인했거나(`premise` = 시험 이름, 이번 기록에서 PASS), 사실 전제가 없는 취향 선택이어야 한다(`premise` = `preference`).
- `fix`: 재현하지 못한 고침은 막는다(`reproduced`가 참이 아니면). 확인 시험은 PASS, `failsBefore`에 고치기 전 판 결과.
- `hardening`: 새 동작·새 화면이 없는 예방만(`noNewBehavior` 참). 새 기능을 예방이라 부르는 길을 막으려는 칸이다.
- `removal`: 뺀 것도 사용자 원문과 이유.

## 4. `open-risks.json` — 시험이 닿지 않는 사용자 경로(손으로, 버전과 상관없이 이어짐)

1.3.0 뒤 저장 뒤 모양 크기·비트맵 레이어 뼈대·확장 없는 `.ent` 픽셀 아트처럼, 가짜 서버 시험이 거치지 않는 길에서 결함이 나왔다.
확인 못 한 사용자 경로(실제 서버 왕복, 확장 없이 열기, 재현 못 한 제보, 코드로만 고친 것)는 찾는 즉시
여기에 `open`으로 적고, 하나라도 `open`이면 관문이 막는다. 닫기:

- `tested`: 그 길을 실제로 거치는 시험 이름 — 이번 전체 시험에서 PASS. 실제 서버 길(`realServer: true`)은 가짜 서버 시험으로 닫을 수 없다.
- `verified`: 실제 환경에서 확인한 증거(`evidence`) + 사용자 확인 원문(`quote`) + 그때 보여 주고 물은 글(`question`). 위임("다 해줘" 등)은 확인이 아니다.
- `probed`: Claude가 실제 환경에서 돌린 탐침 — 증거(`evidence`) + 저장소의 탐침 파일(`probe`, 보통 `tests/real-server/`). 처음엔 이런 확인을 사용자 위임 답으로 `verified`에 넣었다(과적합 검토 지적).
- 탐침을 근거로 쓰는 항목(`probed`, `probe`가 있는 `verified`)은 **실행기가 남긴 탐침 실행 기록**(`release/probe-runs.json` — `node tests/run.js --cases=tests/real-server`)에서 탐침마다 지금 확장 지문·지금 탐침 파일 지문으로 PASS여야 한다. 판이 바뀌면 탐침을 다시 돌린다(과적합 검토 2차 — 앞 판 탐침이 그 뒤 바뀐 저장 길을 계속 닫고 있었음, 3차 — 처음 고침은 사람이 지문을 적어 탐침 없이도 닫혔음).
- `tests/known-limits`(지금 판에서도 실패하는 알려진 한계)의 시험 파일마다 그것을 가리키는(`knownLimit`) 항목이 `accepted`(사용자 원문 + 질문 글)여야 한다(과적합 검토 3차 — 한계 폴더가 기계로 이어지지 않았음).
- `accepted`: 사용자가 결과를 알고 받아들인 원문(`quote`) + 결과 설명(`consequence`). 내 선택지에 대한 답이면(`fromOption`) 그 질문 글(`question`)도. 원인을 모르는 제보는 "된 것 같다"로 `verified`에 넣지 않고 여기에.

## 5. 공개 사본(GitHub) 올리기 전 검사

이 폴더의 기록에는 사용자 원문 인용과 실제 서버 확인 기록이 그대로 들어간다(관문 근거). 공개 저장소에 올릴 사본에는 욕설·엔트리 작품 번호·올린
그림 파일 이름·내 컴퓨터 경로·이메일이 남으면 안 된다(1.3.1 사본에 욕설 인용·비공개 작품 번호가 들어간 채 "올리세요"라고 할 뻔함).
사본을 맞춘 뒤 `node tools/public-copy-check.js <사본 폴더>`가 통과해야 올리라고 한다. 걸린 곳은 사본에서만
고친다(이 폴더 기록은 원문 그대로). 자기 점검: `node tools/public-copy-check.js --self-test`. 이 검사는 정해 둔 종류(욕설·작품 번호·그림 파일 이름·
컴퓨터 경로·이메일·개인 식별 낱말)만 잡는 바닥이다 — 그 밖의 공개 위험은 6절의 과적합 검토가 "남이 보면 안 될 것 전반"으로 본다(이 검사 자체가 그
사고에서 본 종류로 만든 과적합이라는 지적).

- 욕설은 한글 자판을 영문 상태로 친 꼴도 본다. 조각 사이 끼움 글자는 기호 목록이 아니라 글자가 아닌 것 넷까지이고 조각 수 제한이 없다(5차 —
  목록 밖 기호와 4·5조각을 놓쳤음). 자기 점검이 ASCII 문장부호 전부를 2~5조각 사이에 끼워 본다.
- 사용자가 알고 그대로 두기로 한 글은 공개하지 않는 `public-accept.txt`(한 줄에 글 하나)에 적는다. `open-risks.json`에 그 글을 가리키는
  `publicAccept` 항목이 `accepted`(사용자 원문 `quote` + 질문 글 `question`)일 때만, 욕설 검사에서만 가린다 — 기록 없는 줄은 걸린 곳으로 내고,
  같은 줄의 경로·이메일 같은 다른 규칙은 그대로 잡는다(4차). 이 파일과 `private-terms.txt`는 점검 틀 지문(6절)에 들어간다.

## 6. `overfit-review-<버전>.json` — 과적합·편향 공격 검토(관문 5단계)

고침·시험·검사가 눈앞의 사례 하나에 맞춰진 채 나간 일이 되풀이됐다(1.2.1 작품 저장 확인, 1.3.1 공개 사본 검사).
판마다 **작성자와 다른 검토자(새 보조 에이전트)**에게 고정 지시문
`overfit-review-prompt.md`를 그대로 넘겨 검토시키고(판마다 달라지는 경로만 덧붙임), 지적을 처리해 기록한다. `pack.ps1`이 보는 것:

지시문 바꿈(1.3.2, 35차 전): 사용자 결정 「검토 시험이 너무 오래 걸리니까 출시 할때 나타나면 안돼는 그런 치명적인 부분만 가볍게 검토하고 수정해야지」
— 회차마다 2~3시간 걸리던 과적합·편향 전반 검토를 **출시하면 안 되는 치명 결함만, 15분 안**(코드 읽기 위주, 실행은 판단이 갈리는 한두 경우, 사용자
「검토 한번에 1시간이나 쳐 걸리지 말고」)으로 줄임(그림·데이터 잃음, 편집기 못 씀·멈춤, 확장만
켜도 엔트리가 깨짐, 공개물에 비공개 정보, 관문이 그런 판을 통과시킴 = high, 나머지는 찾으면 low로만). 처리는 high만 고치고 나머지는 이유를 적어 기록.
보고서 지문 두 줄·`id:` 줄·`심각도:` 줄 꼴은 그대로(관문이 읽음). 검토 범위를 작성자가 사고마다 줄이는 것이 아니라 사용자가 정한 바꿈이다.

- `promptHash` = 지금 `overfit-review-prompt.md`의 SHA-256 — 작성자가 사고마다 검토 범위를 줄여 쓰면 다시 편향되므로 지시문은 고정. 바꾸면 다시 검토.
- `contentHash` = 지금 확장 파일 지문(전체 시험 기록과 같은 방법) — 검토 뒤 확장을 고치면 다시 검토.
- `harnessHash` = 점검 틀 지문 — 검토 뒤 시험·탐침·검사·관문을 고치면 다시 검토(검토받은 점검 틀과 실제 점검 틀이 같게). 범위는 `tools/gate-hashes.js`의
  `HARNESS_SCOPE` 한 곳에서 정하고 자기 점검이 아래 줄과 대조한다(끝이 `/`면 그 아래 모든 파일, `release/`의 두 파일은 있을 때만).
  지문 범위(harnessHash): `tests/run.js` `tests/lib/` `tests/cases/` `tests/fixtures/` `tests/real-server/` `tests/fixture-makers/` `tests/known-limits/` `tools/` `pack.ps1` `release/public-accept.txt` `release/private-terms.txt`
- `reviewer`, `checked`(확인한 곳 목록 — 찾은 게 없을 때 "없다"만 적는 것을 막음), 지적마다 `fixed`(이번 전체 시험 PASS인 `test`)·`hardening`·`wontfix`·`not-a-bug`(`reason`).
- `report` = 검토자 보고서 원문을 고치지 않고 둔 파일(보통 `release/overfit-report-<버전>-r<회차>.md`), `reportHash` = 그 파일 SHA-256. 보고서의 지적 줄(`id: …`, 지시문 보고 형식)이 모두 기록에 있어야 한다 — 작성자가 지적을 빼고 옮겨 적는 길을 막음(과적합 검토 2차). 보고서도 공개하지 않는다.
- 기록의 `contentHash`·`harnessHash`·`promptHash`는 검토자가 보고서 맨 앞(첫 지적 줄 전)에 한 번씩 적은 「검토 시작 지문:」「검토 끝 지문:」 두 줄과 같아야 하고, 두 줄끼리도 네 지문이 같아야 한다 — 기록 지문은 작성자가 적으므로, 지금 값과만 견주면 검토를 맡긴 뒤 점검 틀을 고치고 기록만 지금 값으로 고쳐도 지나갔다(23차: 검토 중에 다른 세션이 시험 실행기를 고침). 보고서 어디든 지문 글자만 있으면 통과시키던 첫 고침은 보고서 끝에 지문을 덧붙여도 지나갔다(24차). 그래서 지시문에 그 두 줄 꼴을 적었다(1.3.2 개발 중 — 검토 범위를 줄이는 바꿈이 아니라 검토자가 본 판을 기록과 묶는 바꿈, 사용자에게 알림).
- `reportSource` = 보고서 원문의 저장소 밖 출처 — 검토 세션의 보조 에이전트 기록(`.jsonl`). 관문이 `node tools/report-source.js <그 파일>`로 그 기록에서 `SubagentHandback`으로 돌려준 글의 SHA-256을 내어 `reportHash`와 같은지 본다. 머리 두 줄과 기록 지문은 모두 저장소 안 글이라, 검토 뒤 점검 틀을 고치고 셋을 함께 고쳐 쓰면 지나갔다(25차). 검토 세션이 원문을 받는 순간 그 기록 경로와 SHA-256을 알려 주고, 작성자는 그 값으로 적는다. 이 기록 파일은 이 컴퓨터의 Claude 세션 기록 폴더에 있어 다른 컴퓨터에서는 관문이 막는다. 기록의 꼴도 본다(26차 — 어느 `.jsonl`이든 `SubagentHandback` 글이면 통과했음): 자리(집 폴더의 Claude 세션 기록 아래 이 저장소 이름표\<세션>\subagents\agent-<id>.jsonl), 메시지 줄마다 그 agentId·isSidechain, 첫 사용자 글이 고정 지시문을 가리킴, 지시문 파일을 가리킨 도구 호출의 결과에 지시문 글(도구와 상관없이 — Read·셸 출력), 셸 도구(Bash·PowerShell 등)로 돌린 `node tools/gate-hashes.js` 결과의 처음·마지막 지문 = 보고서 머리 두 줄, 상위 세션 기록에 그 agentId, 마지막 도구 호출이 `SubagentHandback`(29차 — 도구 이름을 Read·Bash로만 봐 다른 도구를 쓴 진짜 검토가 막힐 수 있었음). 이 컴퓨터의 파일은 고쳐 쓸 수 있어 이 검사는 위조를 막지 못하고 위조 비용을 올릴 뿐이다(29차 — 저장소 밖 가짜 집에 꼴만 맞춘 다섯 줄 기록이 통과함).
- 회차가 여럿이면 `release/overfit-report-<버전>*.md` 모두가 묶여야 한다: 마지막 회차는 이 기록의 `report`, 중간 회차는 `review-<버전>.json`의 `reports`. 어느 회차든 지적 줄이 두 기록 중 하나에 있어야 하고, 원문이 기록 뒤 바뀌면 막는다(5차 — 중간 회차는 상태·이유만 봤음).
- 보고서에서 심각도 high인 지적은 `fixed`가 아니면 상태(`wontfix`·`not-a-bug`·`hardening`)와 상관없이 사용자 원문(`quote`)과 그때 물은 글(`question`)이 있어야 닫힌다(3·4차). 회차와 상관없이 같다(5차).

## 7. `base-run.json` — 고치기 전 판 실행 기록(관문 6단계)

바뀐 점 기록의 `fix`, 검토·과적합 기록의 `fixed` 지적은 확인 시험이 **직전 출시판에서 실패**해야 그 고침의 근거가 된다(3차 — 사람이 쓴 `failsBefore` 글만 보고, 상관없는 통과 시험을 적어도 막지 못했음). 직전 출시판 zip을 푼 폴더로 `node tests/run.js --ext=<폴더> --base-record <시험 이름…>`를 돌리면 실행기가 그 판 지문(`baseContentHash`)·시험별 결과·시험 파일 지문을 남긴다. 관문은 `changes-<버전>.json`의 `baseContentHash`와 같은 판인지, 그 시험이 PASS가 아닌지, 그 뒤 시험 파일이 안 바뀌었는지 본다. 시험만 바꾼 지적(확장 동작은 그대로)은 `fixed`가 아니라 `hardening`으로 적는다.

- `failCheck`(확인 이름)를 적으면 시험 전체가 아니라 **그 확인**이 고치기 전 판에서 실패했어야 한다 — 시험 안 다른 확인의 실패로 지나가지 않게. 실행 기록은 시험마다 확인 이름과 통과 여부(`checks`)를 남긴다.
- 실행 기록은 시험 파일 지문과 함께 그 시험이 쓰는 `tests/lib` 파일(그 lib이 쓰는 lib까지) 지문(`libHash`)을 남긴다. 확인의 판단이 공용 도구에 있으면 기록 뒤 도구만 고쳐 그 확인을 바꿔도 지나갔다(25차). 쓰는 도구는 `tools/gate-hashes.js testLibs`가 시험 파일을 자식 node로 불러 실제로 불린 `tests/lib` 파일을 모으고(require 꼴과 상관없음), 불러오지 못하면 글자로 찾으며, lib을 가리키는 글자가 있는데 하나도 못 찾으면 오류로 막는다(26차 — 정규식 세 꼴만 보던 것). 관문(`pack.ps1`)은 같은 함수(`node tools/gate-hashes.js --lib`)로 지금 지문을 내어 기록의 `libHash`와 견준다 — 다르면 다시 돌려야 하고, lib을 안 쓰는 시험은 둘 다 없음(null)이라 통과. 미확인 경로 탐침 기록(`probe-runs.json`)도 같다. 실행기(`tests/run.js`, 시험이 불러오지 않는 `tests/lib/harness.js` — 브라우저 띄우기·확인 결과 적기)는 기록마다 묶지 않는다: 바꾸면 `testsHash`·`harnessHash`가 바뀌어 전체 시험과 과적합 검토를 다시 받아야 하는 것으로 묶는다(기록마다 묶으면 실행기를 고칠 때마다 모든 고치기 전 판 기록을 다시 떠야 함).
- 이번 판 개발 중에 생긴 회귀(`regression: true`)는 직전 출시판에서 통과하므로, 그 회귀가 있던 개발판 지문(`devBase`)과 `failCheck`가 있어야 하고 `release/dev-base-run.json`의 그 판 기록에서 그 확인이 실패했어야 한다(6차 — 회귀 지적의 근거가 상관없는 확인의 1.3.1 실패였음). 기록: 그 개발판 폴더로 `node tests/run.js --ext=<폴더> --dev-base-record <시험 이름…>`. `devBase`가 직전 출시판과 같으면 막는다.

자기 점검(`tools/release-gate-selftest.ps1`, 원문 출처·시험 도구 지문 경우는 막힌 이유 글도 봄 — 다른 까닭으로 먼저 막혀 그 검사에 닿지 않은 채 통과로 세지 않게)에 기록 없음·지문 다름(확장·시험·점검 틀)·지시문 바뀜·확인한 곳 없음·처리 안 된 지적·시험 없는 fixed·보고서 원문 없음·보고서 고침·검토 뒤 점검 틀을 고치고 기록 지문만 고침·보고서 끝에 새 지문 줄 덧붙임·머리 지문 비어 있음·시작·끝 지문 다름·머리 지문과 기록을 함께 고쳐 써 저장소 밖 원문과 다름·원문 출처(`reportSource`) 없음·보고서 지적을 기록에서 뺌·high 지적을 원문 없이 wontfix·not-a-bug·hardening으로 닫음, 중간 회차 보고서의 지적 뺌·원문 고침·high를 원문 없이 닫음·묶지 않은 회차 보고서, 미확인 경로의 질문 글 없는 verified·탐침 파일 없는 probed·탐침 실행 기록 없음·실패·옛 판 탐침(probed·verified)·탐침 뒤 탐침 파일 고침·탐침 뒤 그 탐침이 쓰는 시험 도구 고침·질문 없는 선택지 accepted·알려진 한계 시험의 막힘 항목 없음, 고치기 전 판 기록 없음·고치기 전에도 통과·기준 판 다름·기록 뒤 시험 파일 바뀜·failCheck가 고치기 전에도 통과·회귀의 개발판 기록 없음·회귀에 failCheck 없음·개발판에서 확인이 통과·개발판 기록 뒤 시험 도구(`tests/lib`) 고침, 기록의 목록 칸이 아예 없는 경우(확인한 곳 칸 없음·탐침 칸 없는 probed — PowerShell 5.1은 없는 칸을 `@()`로 감싸면 항목 1개로 세어, 관문이 칸 없는 확인한 곳을 지나치고 탐침 칸 없는 verified·probed에서 알림 없이 멈췄다. 관문은 목록 칸을 모두 `Get-Items`로 읽는다), 그리고 위 지문 범위 줄과 `HARNESS_SCOPE` 대조가 있다. 관문이 알림 없이 끝나면 자기 점검이 첫 출력 줄을 보인다.

공개 사본은 `node tools/sync-public-copy.js <사본 폴더>`로만 맞춘다 — 허용 목록(`tools/public-files.js`) 파일만 복사하고 이 폴더의 기록(`*.json`)은 공개하지 않으며, 마지막에 공개 전 검사가 통과해야 한다. 개인 식별 낱말은 공개하지 않는 `private-terms.txt`에서 읽는다.

## 한계(정직하게)

관문은 기록의 **형식과 시험 결과**만 기계적으로 확인한다. 바뀐 점 기록의 원문이 정말 그 사용자 말인지, `preference`가 정말 취향 선택인지도
기계는 모른다 — 기록은 사람이 읽고 따질 수 있는 근거로 남기는 것이다. 검토가 실제로 충분히 깊었는지, `fixed` 시험이 그 버그를 정말 잡는지는
확인하지 못한다 — 그래서 검토 기록에는 음성 대조(고치기 전 판에서 실패) 결과를 같이 적는다. 사용자의 실제 크롬 사용 확인은 별도다.

자기 점검: `powershell -ExecutionPolicy Bypass -File tools\release-gate-selftest.ps1` — 기록이 없거나·낡았거나·처리 안 된 지적이 있으면 관문이
실제로 막는지 임시 폴더에서 돌려 본다.
